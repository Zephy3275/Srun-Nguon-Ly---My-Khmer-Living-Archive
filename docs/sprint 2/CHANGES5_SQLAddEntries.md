# CHANGES 5 — Your entries move in: 9 rows into `entries` (Sprint 2)

Session log for **Lab 6, Part 2**: moving the 9 Sprint 1 entries from
`data/entries.js` into the Supabase `entries` table created in
`CHANGES5_SQL.md`. No application code or repo file was changed; the INSERT was
run by hand in the Supabase dashboard SQL Editor. The app still reads
`data/entries.js` (see Heads-up).

---

## 1. What changed

- **Supabase (dashboard, not the repo):** 9 rows inserted into `entries`, one per
  entry in `data/entries.js`.
- **Repo:** only this changelog is new. `data/entries.js`, app code,
  `package.json` and `.env.local` are untouched.

## 2. How the INSERT was produced

- The SQL was **generated by a script from `entries.js`**, not retyped, so the
  Khmer text is copied byte for byte. Nothing was written into the repo; the
  script and output lived in a scratch folder.
- The script checked, programmatically, that every title, Khmer title,
  description, Khmer description, source and photo path appears verbatim in the
  SQL (after SQL escaping), and that all 9 photo files exist in `public/images`.
- The multi-part `"..." + "..."` description strings were joined into single
  values.
- Apostrophes were escaped for SQL (`uncle''s`, `yolk''s`, `it''s`).

## 3. Field mapping

| `entries.js` | column | notes |
|---|---|---|
| `title`, `titleKhmer` | `title`, `title_khmer` | direct |
| `description`, `descriptionKhmer` | `description`, `description_khmer` | direct |
| `source` | `source` | direct |
| `image` | `photo_url` | copied exactly, e.g. `/images/Moocake_BigPeah.jpg` (the filename typo matches the real file) |
| `id` (slug) | dropped | the database generates a uuid instead |
| `taste`, `ingredients` | not migrated | `taste` was placeholder in all 9 entries (`scale: 3, notes: ""`) and `ingredients` was empty, so `texture`, `sweetness` and `saltiness` are **null** |
| none | `filling`, `shape`, `color` | new, see below |
| none | `owner` | see below |

## 4. Values that were not in `entries.js`

`filling`, `shape` and `color` are `not null` but did not exist as fields, and
heritage content is never invented (AGENTS.md rule 6). Claude looked at all 9
photos and read the descriptions, proposed a value per entry, and the student
reviewed and approved them (with one correction: Round Peah color changed to
match the other Peah entries).

| Egg 2 | mixed nuts and seeds | square | golden-brown |
| Bean Paste Egg 1 | bean paste | round | golden-brown |
| Lotus Paste Egg 1 | lotus paste | round | golden-brown |
| Lotus Paste Egg 2 | lotus paste | round | golden-brown |
| Pandan Lotus Paste Egg 1 | lotus paste | square | green |

### Judgment calls

- **Egg 1 and Egg 2 filling** is the generic "mixed nuts and seeds." The
  description says it is *likely* a five-kernel blend, still being confirmed with
  family, so the more specific claim was not made. Update once confirmed.
- **Pia fillings** are stored as one slash-separated text value,
  `taro/bean/winter melon`, because the customer picks one of three. Trade-off:
  it cannot be filtered by a single filling later without splitting the text.
- **Pandan Lotus shape** is `square` (it looks slightly rectangular).
- **Peah colors** all use "pale cream with red stamp." The Round Peah photo looks
  more golden, but the student chose consistency across the three Peah entries.

## Caveats

- The dashboard runs as a privileged role and **bypasses RLS**, so this insert
  succeeding says nothing about the policies. They are first exercised when the
  app writes as a logged-in user (week 7).
- Undoing an insert is harder than running one. If a row needs fixing, prefer an
  `update` on that row over deleting and re-inserting, and re-running the same
  INSERT would create 9 duplicates (there is no unique constraint).

## Heads-up for later

- **The app still reads `data/entries.js`, not the database.** Nothing on the
  site changed. Reading from Supabase is a later step.
- **URLs will change.** The `/entries/[id]` route currently uses slugs like
  `mooncake-egg-1`. The new rows have uuid ids, so that route and its links
  must change when the app reads from the database.
- **Naming mapping:** `entries.js` is camelCase (`titleKhmer`, `descriptionKhmer`,
  `image`); the table is snake_case (`title_khmer`, `description_khmer`,
  `photo_url`).
- `texture`, `sweetness` and `saltiness` are empty until real tasting data exists.
